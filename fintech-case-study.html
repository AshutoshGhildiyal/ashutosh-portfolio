The JSON contract is a proposal, not the current endpoint. Money should use decimal-safe representations (such as BigDecimal) and explicit currency rules; avoid binary floating-point for financial amounts.

Success response

  "transactionId": "...",
  "status": "COMPLETED"
}

Illustrative response shape; adapt to the actual DTO.

Error contract

400 invalid input · 404 account not found · 409 insufficient balance or duplicate idempotency key · 500 unexpected failure.

Choose status codes consistently and document the exact error body.

04 / DATA MODEL

Data ownership & consistency

Keep money movement auditable. The following is a recommended schema outline to validate against the actual entities and migrations.

accounts

Owns the current account state.

id · user_id · balance · status · versionUse optimistic locking or an appropriate row-level locking strategy for concurrent updates.
transactions

Tracks the transfer request and lifecycle.

id · sender_id · receiver_id · amount · status · created_atStore enough metadata to investigate failed and repeated requests.
ledger_entries

Append-only record of financial movements.

id · transaction_id · account_id · debit · credit · created_atUse balanced double-entry postings and enforce invariants in the transaction boundary.
idempotency_records · proposed

Stores request key and its result.

key · request_hash · status · response_refEnforce uniqueness at the database level and define key expiry and mismatch behavior.
CORE INVARIANTA transfer must not create or destroy value.

For a completed transfer, the sender debit and receiver credit must reconcile. Keep ledger writes and the corresponding state transition atomic wherever they share a database.

05 / FAILURE & RECOVERY

What happens when things fail?

This is where the design becomes more than a happy-path demo.

Failure scenarioExpected handlingDesign consideration
Insufficient balanceReject before committing debit.Atomic conditional update or lock; return a clear domain error.
Concurrent transfersPrevent lost updates and negative balance.Optimistic version check or row lock; retry conflicts safely.
Client retries after timeoutReturn the existing result for the same key.Persist idempotency key and result with a unique constraint.
Debit succeeds, credit failsDo not blindly repeat the debit.Prefer a single local transaction where possible; otherwise model saga state and compensation.
Event published but DB write failsAvoid inconsistent event/data state.Use a transactional outbox when asynchronous publishing is introduced.
Downstream consumer unavailableRetry with limits and track exhausted events.Backoff, dead-letter handling, idempotent consumers, and alerting.
06 / ENGINEERING DECISIONS

Trade-offs to explain in an interview

Monolith vs microservices

Separate services clarify ownership and independent scaling, but introduce network failures, deployment complexity, and cross-service consistency work. Start with boundaries justified by the domain, not by fashion.

Optimistic vs pessimistic locking

Optimistic locking is useful when conflicts are relatively rare; pessimistic locks can suit highly contended records but may reduce throughput and create lock waits. Measure and test realistic contention.

Synchronous vs asynchronous work

Keep the critical transfer decision synchronous when the caller needs a definitive result. Use events for independent downstream work such as notifications and analytics.

Cache vs source of truth

Redis may accelerate reads or rate limits, but account balances require authoritative, transactionally consistent storage. Never let a stale cache decide whether funds are available.
